## 2. 破坏面清单

本任务新增的"能删文件/移动文件/写盘/联网"代码路径，逐条列出：

1. **启动恢复（recover.rs）——本任务唯一新增的文件移动面**。四分支决策表：
   - ① manifest 有 Quarantined 记录 → `restore_one`（**100% 复用** P4-02 四重校验：隔离区根内/sha256/白名单禁区/父链 reparse）。**journal 不参与任何路径决策，只决定"查哪条 manifest 记录"**（按 original_path 精确匹配）——伪造 journal 无法让应用触碰不在 manifest 里的文件（T-6 核心）；
   - ② manifest 有终态记录 → 无动作；
   - ③ 原路径仍存在 → 无动作（移动前崩溃，文件未受影响）；
   - ④ 「已移入未登记」窗口 → `adopt_into_manifest` **只写一行 manifest（add_manifest_entry），不移动/不删除任何文件**；候选必须满足：文件名 `<8 位十六进制>_<原名>`（store 命名约定）、深度 ≤3、未被任何 manifest 行引用、**且唯一**——不唯一即拒绝并记失败。补登记等级强制 🟡（可还原语义），**不自动还原**。
2. **不可逆去向（direct/recycle）孤儿**：只追加 journal result（ok=false，orphan 标记）+ 审计，**零文件操作**（SAFETY §3 规则 2：🟢 类可重建损害可控）。
3. **journal 写入**：`close_intent` 经 `Journal::open`（只追加 O_APPEND，seq 续编）；无重写、无删除。
4. **dump 目录写入/清理**：崩溃处理器写 `<data_root>\crash\*.dmp(+.json)`；`prune_old_dumps` 启动时仅删该目录内保留期外的 `.dmp` 与同名 `.json`。不动其他路径。
5. **`crash_upload`**：读 crash 目录内经文件名白名单校验的 dump + `http_post` 发送；**opt-in 门禁**（`crashUploadOptIn=false` 直接拒绝，红线 #4：仅 R22/R24 两处联网）；体积上限 50MB；成功/失败均记审计。
6. **`clean_execute` 门闸（收窄既有破坏面）**：恢复期（`recovery_pending=true`）拒绝新清理事务——防止恢复移动文件与新清理竞态。
7. **无注册表/进程操作**：本任务零注册表写入；无杀进程代码（crash-sim 的 `seh` 模式是对自身进程的测试触发，非产品路径）。
8. **crash-sim CLI 面收敛**（安全扫描拦截后加固）：初版 `clean` 接受 3 个路径参数，安全扫描判定为 path-traversal 入口（运行时护栏不满足静态扫描）；终版 **CLI 零路径参数**——全部工作目录派生自 `PURESLATE_DATA_ROOT`（env 信任面等价既有 LOCALAPPDATA），txId 走字符白名单。该二进制不存在对调用方指定路径的移动/写盘能力。

**T-6 攻击面自查**（评审重点）：
- 伪造 journal 路径指向白名单区文件 → 恢复只会在 manifest 中查找该路径的记录；manifest 无记录 → 走分支③/④；分支④要求隔离区内存在未被引用的同名约定文件——白名单区不在隔离区内，无候选 → 记失败，零动作。已测（`tampered_manifest_recovery_is_refused_by_t2`：篡改 manifest originalPath 指向 system32 → restore_one 白名单校验拒绝，`tests/crash_safety.rs` 与 recover 单测双层覆盖）。
- 伪造"唯一候选"：攻击者预置 `deadbeef_<名>` 文件于隔离区 + 伪造 journal → 后果仅为**把该文件登记进隔离区 manifest**（🟡，14 天可还原/可清除），原路径不受影响、无越界移动。风险上限 = 隔离区多一条假记录，用户可见可清。

### 3.2 kill 测试设计（SAFETY §6.3 边界 7「操作中途 kill 进程」）

`crash-sim clean` 子进程逐文件执行与生产 `execute()` 相同的模块序列（真实 `Journal` + 真实 `move_into_quarantine`）：`intent → 移入隔离区（写 manifest）→ 停 300ms → result`；父进程轮询 marker（第 3 个文件移入后写）出现即 `kill()`——确定性构造「intent+manifest 已写、result 未写」的真实 kill 窗口形态（隔离区根显式传沙箱路径，不触碰真实卷根；偏差已在注释声明）。父进程扮演"下一次启动"：

- `report.orphans_found == 1`（恰一个 in-flight 孤儿）；
- `report.restored == 1`，`sample-02.tmp` **已还原回原路径**，manifest 行 `state=Restored`；
- 已完成的前 2 项留在隔离区（清理语义不回滚）、未开始的 5 项原样；
- `detect_orphans()` 空（journal 全闭环）、审计含 op=recover 记录。

**SEH 通道**（`crash-sim seh`）：volatile 空指针写触发真实硬件访问违规 → 过滤器快照上下文 → 辅助线程落盘（sidecar 异常代码 `0xC0000005`）→ 进程被内核终止（实测退出码映射 SIGSEGV/139）。**panic 通道**：hook 落盘无异常流、无 sidecar，退出码 101。

### 3.4 已知限制（如实声明）

1. `MiniDumpWriteDump` 异常流路径在本机环境不可用（恒 998 ERROR_NOACCESS，故障线程直调与辅助线程+自有快照均复现）——异常代码改经 sidecar 携带，dump 本体保证落盘（LESSONS §① 详录）；
2. 堆损坏/fastfail（`std::process::abort`）类崩溃超出进程内处理器能力，v1 不覆盖（记录于 dump.rs 头注释；后续可评估独立转储进程）；
3. 上传端点为 `.invalid` 占位（P4-06 定稿），当前"上传"必然优雅失败且记审计；
4. 真机人工走查项：双开验证不受影响（P4-02 项）、Settings 崩溃卡片预览/上传流、Home 恢复横幅（可用 mock 模式预览）。
