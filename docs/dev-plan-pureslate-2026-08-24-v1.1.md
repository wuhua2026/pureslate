## 2. 单人+AI 执行模式（本版核心改造）

### 2.1 HPW 账目单位

**HPW（人工当量周）只计人的时间**：需求拆解、prompt 编写、AI 产出验证、真机测试、决策。**不含 AI 生成时间**——AI 出 800 行代码只需你 10 分钟审查，计 10 分钟。
原 pw 单位下的「协调开销 15%」归零，但新增「AI 产出验证开销」，已在分档中吸收。

### 2.2 AI 提效三档（任务级分类，账目基础）

| 档位 | 提效比 | 任务特征 | 典型任务 |
|------|--------|----------|----------|
| **α ×3–4** | 高 | 模式化、有明确验收、可 mock 验证 | UI 页、mock 数据、CI/签名流水线、文档、物料初稿 |
| **β ×2** | 中 | 结构清晰、可单测覆盖、逻辑为主 | 规则引擎、分级、日志、更新机制、hash 扫描 |
| **γ ×1–1.2** | 低/无 | Windows 深水区、错误隐蔽、真机才能验证 | 隔离区还原、兼容加固、进程守卫、事务回滚、崩溃安全 |

> **判断原则**：AI 会生成「似是而非」的 γ 类代码——编译通过、happy path 正常、边界条件错。γ 类的真实成本在**真机验证与失败用例构造**，省不掉。单人模式的瓶颈从「编码」转移到「验证和判断」。

### 2.3 工作流：主线 + AI 支线

```
开发者（主线，串行推进内核任务）
   │  每个内核任务的空档（等编译/等测试/精力低谷）
   └─→ AI 支线会话（并行处理不依赖主线的任务）
        ├─ UI 页（依赖已冻结的 IPC 契约 + mock，不依赖内核进度）
        ├─ 文档/数据流向图/issue 模板
        ├─ CI/签名流水线/R26
        └─ 物料三件套初稿
```

原 v1.0 的「B 泳道」整体转化为 AI 支线，**IPC 契约 + mock 冻结（M0）仍是支线解耦的生命线**。

### 2.4 三道关 Review（替代双人 PR 互审）

所有代码合并前：

- **关 1 · 生成**：主会话 AI 生成（带完整上下文）；
- **关 2 · 独立评审**：**新开会话**（不带生成上下文）的 AI review——只给代码+需求说明，问「这段代码有哪些路径会丢数据/破坏文件/卡死」；
- **关 3 · 人工精读**：开发者本人读关键路径。

**关 3 必读清单（破坏性操作模块，一行都不能跳）**：R04 删除路径、R25 移入/还原/清空、R08 隐私清理、R23 进程守卫、R24 事务回滚。其余模块抽查。

> 单人开发最大的风险是「自己（的 AI）写的删除代码自己看不出来问题」——上下文污染。关 2 的独立性是 antidote，**禁止**用生成代码的同一会话做 review。
> 每次 AI 产出要求附带「**本次改动破坏面清单**」（哪些函数能删文件/改注册表/终止进程），关 3 按清单核对。

### 2.5 指导者评审 → 社区公开评审（W13–14）

- 破坏性操作代码（关 3 清单模块）在 M3 前发布到 V2EX / Rust 中文社区求公开 review；
- 🔴 白名单核定：以微软官方文档 + 社区评审意见为准，记录在 `docs/safety-whitelist.md` 并开放 issue 反馈；
- VM 回归环境：微软官方免费开发者 VM 镜像（90 天评估版 Win10/Win11，支持快照），替代原「指导者提供环境」。

## 3. Spike 三件套（W1–3 前置验证，新增）

> 原计划无此环节。三个 Spike 的实测数据比文档中任何假设都值钱——**Spike 2 的结果直接决定 R01 架构**。

| Spike | 窗口 | 内容 | 决策点 |
|-------|------|------|--------|
| **S1 · 技术栈地基** | W1 | Tauri 脚手架 + IPC hello world + 真机打包 | 包体 <20MB 验证；WebView2 依赖在国内环境的安装体验；失败 → 评估 Wails/Electron（后者放弃，体积超标） |
| **S2 · 扫描性能**（最关键） | W2 | `walkdir` 在本机（样本 #0：双盘 75% 满载）全盘遍历计时；SSD+HDD 各测 | **若 SSD >120s/1TB → R01 必须采用 MFT 直读**（`ntfs` crate / USN 枚举，需管理员权限），R01 账目 +1.5 HPW，安装包声明管理员权限要求；同时确定 M3 的 HDD 参考口径 |
| **S3 · 破坏性 API 路径** | W2–3（随行） | 回收站删除+还原 API、跨盘 move、文件占用检测、manifest 读写 | 验证 R25/R04 的核心 API 可行性；发现坑提前计入 T4/T6 账目 |

## 6. 关键依赖与并行解耦

```
IPC 契约冻结(W1) ──┬─→ 主线全部内核任务
                   └─→ AI 支线全部任务（mock 解耦，不等内核）
Spike 2 性能实测(W2) ─→ R01 架构定案（walkdir vs MFT）─→ [M1]
R01 ─→ R02 ─→ R03 ─→ [M1]
R25 核心(W5-6) ─→ R09 ─→ R04 ─→ [M2]        ← 信任先行链（不变）
R21 框架随行 ─→ W14 VM 快照回归 ─→ [M4]
R26(W12-13) ─→ W16 签名发布 ─→ [M5]
```

- **唯一阻塞点**：W1 契约未冻结 = 主线与支线全停 → M0 仍是第一优先级；
- AI 支线全程 mock 驱动，理论上不受主线拖累；**支线是精力低谷期的填充物**，主线状态好时优先主线；
- 主线性能验证（W8）若不达标，先优化（规则缓存/增量加载/**MFT 直读**），**不裁范围**——M3 是硬门禁。
